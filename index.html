    The problem

    Decode is a long chain of kernel launches.

    Autoregressive decoding produces one token per forward pass. At small batch sizes that pass is memory-bandwidth bound: the GPU streams every weight from HBM once per token, so the floor is weight bytes divided by memory bandwidth. A decode step in eager PyTorch is hundreds to thousands of separate launches. torch.compile fuses some of them, and CUDA graphs remove most of the CPU launch overhead. The GPU still runs a chain of kernels, and every boundary costs something.

    1. A full barrier and a memory flush

      Every streaming multiprocessor waits for the slowest thread block before downstream work can start, including work whose inputs are already finished.

    2. Cold pipelines

      Each matrix multiply refills its load pipeline from empty. The next layer waits for its own launch, and shared memory does not survive across kernels.

    3. Stranded SMs

      A small projection that occupies part of the GPU leaves the rest idle, and that idle capacity cannot pick up future work.

    The known answer is a megakernel: one persistent kernel that runs the whole model, with fine-grained dependencies in place of kernel boundaries. Hand-written megakernels have shown large decode speedups on H100 and B200. Each one takes specialists weeks to months, is tied to one architecture on one GPU, and goes stale with the next model release.

    What MegaBake does

    The megakernel is a compiler output.

    1. Capture through PyTorch’s own stack

      TorchDynamo captures the call. AOT and post-grad passes normalize the FX graph. MegaBake takes the graph where Inductor would lower it, and keeps guards, aliasing, mutations, and outputs.

    2. Recover what the graph computes

      Regions carry explicit layouts, dependencies, state effects, and numeric requirements. Coverage comes from operator families and declared ops, including attention through transformers’ AttentionInterface. A new architecture compiles by extending those families.

    3. Compose tuned device code

      Each region maps to a body in NVIDIA’s CuTe DSL. Matrix multiplies use a Hopper TMA/WGMMA pipeline, with a small-batch variant. Decode attention splits long contexts across SMs. Norms, RoPE, and activations fold into their consumers. The tuned pipeline stays intact inside the composed kernel.

    4. Plan one persistent kernel

      MegaBake decides which tiles each SM computes, when, in which shared or global buffers, and with what synchronization.

    5. Verify before use

      The captured graph is the correctness reference. An unsupported graph fails with a clear message, or the whole invocation falls back to torch.compile. Numerics stay labeled either way.

    Still on the table

    The launch cost is the first slice of the gain.

    So far MegaBake has mostly removed launch and dispatch cost. Larger gains come from schedules a chain of kernels cannot express. These are engineering estimates, not measurements yet. Bandwidth use is about 50% on SmolLM-1.7B.

    Optimization What it changes Estimated gain
    Tile-level dataflow Each SM waits only on the tiles it consumes, using event counters in place of grid-wide barriers. 5–30% lower GPU time
    Cross-layer weight streaming Waiting SMs prefetch the next layer’s weights while the current layer computes, so GEMM pipelines stay warm across layers. A further 8–15% on larger models
    On-device multi-step decoding Sampling and the next embedding run inside the kernel, so several tokens are generated per launch. 10–25% per token end to end
    In-kernel speculative verification At batch 1, verifying 8 draft tokens costs about the same weight traffic as verifying 1. 2–4× tokens per second

    Working today

    • Eight Hugging Face decoders compile into one persistent CUDA kernel for stateful decode. Prefill support varies by model.
    • Outputs are checked against PyTorch. SmolLM-135M and Qwen2-0.5B match eager bf16 across advancing decode calls.
    • Hopper, bf16. Static shapes, with megabake.bucketed covering a few prompt and batch lengths.

    Why this matters

    Compile through torch.compile.

    A backend beside Inductor
    MegaBake plugs in at the same handoff and keeps PyTorch’s guarantees about guards, aliasing, and state. The Dynamo/FX stack can schedule a whole model, not only emit one kernel per operator.
    Support for new architectures
    Models change every few weeks: new norms, RoPE variants, attention forms. MegaBake matches by semantics. Adding a model is an extension of the operator families.
    Hardware as a body provider
    The graph, the execution plan, and the device bodies are separate. Hopper is the body that runs today. Blackwell, Ampere, and other accelerators plug in behind the same compiler.
    Compiled once, then distributed
    A baked kernel is tied to one model revision, one shape bucket, and one GPU class, and it takes minutes to produce. The Hugging Face Hub already pins revisions and ships architecture-matched kernels. The proposal is to publish MegaBake’s device bodies on the Kernel Hub, and one verified megakernel per model revision next to the weights.
